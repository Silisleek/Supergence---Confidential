Know your way around the workspace +

Conversations holds recent tasks. Search with Ctrl / Cmd K. Open Browser opens the shared browsing surface; name the page and action you want. Open Files helps inspect project files. The Learning library is a place to carry knowledge forward; ask Supergence to read relevant material rather than assuming it knows every previous conversation.

Enter sends a message; Shift Enter adds a line. The microphone supports dictation when microphone access is available. The question-mark button opens Help & shortcuts, including this guide.

02 / WRITE WITH INTENT

Four things that make a useful brief.

Plain language works. Tell Supergence what matters; it can help you work out the rest.

01

The outcome

What should exist when the task is finished?

“A two-page proposal for a school garden.”
02

The context

Who is it for, and what should it work from?

“For the headteacher. Use the attached budget.”
03

The boundaries

What must it include, preserve, or work within?

“Under ₹20,000. Keep maintenance simple.”
04

The finish line

What format and checks make the result useful?

“Include costs, a timeline, and open questions.”
MAKE THE ASK MORE CONCRETE
A loose starting point

“Make this website better.”

A direction it can act on

“Improve the mobile navigation on this site. Keep the existing colors and content. Make the menu usable with a keyboard and check it at 390px and 1440px.”

For a simple question, just ask it. For a large project, add milestones and agree on what the first version should do. A longer prompt helps only when its details are relevant.

05 / GET TO A BETTER RESULT

Give feedback the work can use.

The first response is something to review. Point to the gap, keep what works, and ask for the next specific improvement.

When the answer is too broad

“Focus on [part]. Use [specific source or file]. Give me [format] for [audience], and label anything you cannot verify.”

When something does not work

“In [file or preview], doing [steps] causes [actual result]. It should [expected result]. Fix the cause, keep [working behavior], and rerun that check.”

When the design is not there yet

“Keep [what works]. Improve [lighting, spacing, materials, or hierarchy] toward [reference]. Show a close view and explain what changed.”

When the task is getting large

“Finish [milestone] first. Keep the original requirements. Save the source and a short progress note with completed checks and remaining work.”

BEFORE YOU CALL IT DONE

Open it. Try it. Check the evidence.

For factual work, inspect the sources and uncertain claims. For code, run the relevant behavior. For a visual, inspect the actual pixels and important views. Ask which checks were run and which remain unverified.

  • A useful file, preview, or answer
  • Evidence for the important claims
  • Working critical interactions
  • A clear account of remaining limits
A few questions worth asking +

Do I have to know the right technical words?

No. Describe what you want someone to see, do, or understand. Examples, screenshots, filenames, and real errors are often more useful than jargon.

Should I ask for a plan or the finished thing?

Say which you want. “Help me compare approaches” invites discussion. “Build this, test it, and give me the files” asks for execution when the necessary tools are enabled.

What if it says it cannot use a tool?

Check the access control and available connections. Ask it to try the relevant installed tool and report the actual error. A prompt cannot supply a missing connection, permission, or model capability.

Does a better prompt guarantee a perfect result?

No. Clear instructions make the goal easier to assess. Complex work can still need several passes, testing, and judgment.
